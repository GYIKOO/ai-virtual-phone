# Float 剧情系统重构路线与验收清单

本文件记录已讨论的产品边界、待实施步骤和验收条件，供后续逐项检查。先优化与聊天互通的单人主线剧情，不改现有线下模式；多人剧情和独立 if 线后续分别推进。

更新日期：2026-10-03。开发分支：`codex/story-system-rework`。已实现剧情工具菜单、导演指令和可附加要求的重试，等待用户在本地测试；未合入 main、未部署。

## 已确认的产品边界

- 线下模式保持现状，定位偏日常相处与角色互动。本次不改它的提示词、界面或记忆规则。
- 主线剧情是角色真实经历的小说式表达，与线上聊天及线下经历双向互通，不默认隔离成创作沙盒。
- 主线剧情提供更自由的叙述者定位、情节推进和未来的状态辅助能力。user 不必始终是镜头中心。
- 字数、长短、人称、有限或全知视角、能否代写 user 的对白动作心理、文风与节奏，均由用户可编辑的预设等配置决定。讨论中的具体字数与视角只是例子，不是底层规则。
- 互通指共享连续经历与事实，不是每次无差别发送全部历史全文；实际使用正文、摘要和长期记忆组织上下文。
- 全知叙述不等于角色全知。正文可以包含角色未知的信息，不能因此直接变成该角色的亲身记忆。
- 未来 if 线用于直接体验 char 与 user 的 AU、平行宇宙和同人 paro，拥有独立设定、历史、关系状态和持续记忆，不自动污染主线。
- if 线不要求用户大量亲自写作，也不必套上“主线角色和 user 一起写小说或玩游戏”的外层设定。该外层形式只是未来可选扩展。

## 第一阶段 梳理并优化单人主线预设

目标：先确认现有剧情支持用户配置的小说式叙事；本阶段是检查与必要的小调整，不重造存档系统。

阶段状态：2026-10-03 完成代码层面审查，可以进入第二阶段。未调用用户模型 API、未读取手机内实际预设或插件配置；不把静态审查等同于实际生成效果验收。默认条目暂不修改，下列创作草案与更新机制工作在确实需要改默认预设时再启用。

- [x] 追踪剧情请求代码链路：绑定解析、默认预设回退、条目开关与标签、宏、世界书、历史与记忆、正则、插件、接口适配。
- [x] 区分用户可编辑的默认提示词、动态注入的数据，以及不可直接编辑的协议或固定文本。
- [x] 静态审查预设界面之外的创作限制；未发现引擎额外强制具体字数、人称或禁止代写 user，发现角色资料固定身份前缀，详见审查结论。
- [ ] 优化默认剧情条目，使其适合小说叙事和情节推进；具体默认文案先讨论再实现。
- [ ] 默认条目允许用户编辑、关闭或替换；不能在引擎中偷偷补回用户已关闭的创作规则。
- [ ] 不覆盖用户现有预设、正则或自定义内容。设计默认预设更新与用户修改的保留方式。
- [x] 确认已有调试面板调用剧情提示词预览；预览不经过发送前插件处理，不能无条件当作最终请求。保留实际发送的调试快照作为排查依据，不重做预览界面。

验收：两套明显不同的剧情预设能分别生效，例如不同篇幅、不同视角、允许或禁止代写 user；不应因不可编辑的内部叙事规则而被强制拉回相同写法。模型不遵循提示词与软件额外注入冲突应分别诊断。

## 第二阶段 导演指令与重试操作

本阶段复用现有单人主线记忆互通，不新增写作讨论或未采纳草案系统。以下跨模块记忆检查保留为后续验收，不作为本轮全局重构任务。

- [x] 输入框左侧提供可展开的剧情工具菜单。
- [x] 导演指令使用独立输入框，保存为默认折叠的特殊记录，不混入扮演正文历史；仅指导对应的一次生成。
- [x] 重试共用输入框，要求可留空；临时要求只进入本次请求，不存入剧情记录。
- [x] 保留长按历史消息重试；成功后才替换选中位置及后续记录，失败或取消保留原文。
- [x] 重试请求排除待替换记录的近期事件投影；编辑时清除旧摘要缓存，不自动删除长期记忆或其他模块经历。
- [x] 提供不调用模型、不写入存档的本地交互预览，并通过类型检查、请求组装测试及移动端浏览器交互测试。
- [ ] 用户确认界面与真实生成效果；长期记忆已有内容不会自动随重试回滚，界面明确提示。

### 后续记忆验收

- [ ] 验证聊天中的新事件能被剧情承接，剧情的事件与关系变化也能返回聊天。
- [ ] 检查近期摘要、全文历史与长期记忆之间的重复、遗漏、顺序和预算。
- [ ] 区分故事事实与角色所知，先明确单人阶段如何处理角色不在场的叙述、秘密及读者已知信息。
- [ ] 区分正文事件与导演指令、写作讨论、未采纳的草案，后者不能自动成为真实经历。
- [ ] 检查编辑、重生成、删除后是否保留了失效摘要或记忆，明确处理与提示方式。
- [ ] 不以“修复剧情记忆”为由删除角色在聊天或其他模块中的独立经历。

验收：聊天到剧情再回聊天，连续性保持一致；重生成废弃的剧情不继续当真；角色不因旁白全知而无条件获知秘密。此阶段不承诺一次解决完整的多人知情模型。

## 第三阶段 章节与叙事操作

- [ ] 讨论主线章节与场景的组织方式，避免把同一角色的章节误当成互不相干的世界。
- [ ] 复用现有续写、编辑、重生成能力，确定缺失的操作后再新增。
- [x] 正文输入与导演指令分离，独立入口已在第二阶段实现。
- [ ] 支持章节或场景摘要，明确它们与现有短期和长期记忆的关系。
- [ ] 设计回退的作用范围和关联记录，不能一键回退剧情就抹掉此后所有聊天。

验收：一条主线可以持续推进、查阅和修订；用户知道哪些内容会进入经历，哪些仅是写作指令。复杂分支树不作为第一版前提。

## 第四阶段 可配置状态与剧情辅助

- [ ] 定义可选状态字段、展示方式和持久化方式，不硬编码某套题材专属字段。
- [ ] 区分展示用状态栏与真正参与下一轮生成的状态数据。
- [ ] 提供可配置、可关闭的剧情推进提示词或规则接入位置。
- [ ] 确保状态随章节历史保存，重生成、编辑和回退不会留下废弃状态。
- [ ] 默认模板只是可编辑起点，不强制采用特定节奏、冲突公式或剧情引擎。

验收：状态在后续回合有效，回退后与正文一致；关闭辅助规则后不再注入。先支持预设驱动，不急着引入复杂的自动运行引擎。

## 后续 多人主线与 if 线

单人主线稳定后再安排先后，不把这两项捆成一个大版本。

### 多人主线

- [ ] 设计参与者、实际出场角色、镜头焦点与时间地点。
- [ ] 区分共同事件和各角色知情范围，避免全员读心或配角失忆。
- [ ] 支持没有 user 在场的场景，不强制所有角色轮流发言。
- [ ] 明确多人经历如何回到各角色的聊天与记忆。

### 独立 if 线

- [ ] 设计 AU 身份与设定覆盖，保留需要的角色特征但不强行继承主线身份和经历。
- [ ] 每条 if 线拥有独立历史、摘要、状态和持续记忆，不能仅靠短期上下文支撑长故事。
- [ ] 明确是否允许从主线某个时点复制起始信息；若允许，应是可控的初始化，而非隐式双向同步。
- [ ] 覆盖生成、检索、总结、导入导出、回退和删除等所有路径的隔离测试。
- [ ] 是否增加“主线角色共同创作或体验 if 故事”的外层玩法，留待实际需求确认。

数据结构可以为故事归属与未来分支预留扩展空间，但本轮不提前实施全局记忆分区，也不开放不完整的 if 模式。

## 现有玩法的复用边界

共创允许用户给简短指令，让 AI 追加或编辑章节，不要求用户大量写正文。其结构区分写作搭档与作品人物，默认是“和角色一起写小说”，不等于直接置身 AU。可以借鉴章节、笔记、修订机制，不能仅因能写同人题材就认定 if 线重复。

冒险有自己的存档、日志、任务进展、世界状态和累计摘要，并非只存在于近期事件中。它向日常记忆提供带跑团游戏标记的摘要；在相应配置和总结条件下，事件也可能成为长期记忆素材。其默认玩法仍是地图跑团与 DM 裁定，不能直接视为自由小说式 AU 系统。

参考代码：`lib/cocreate-types.ts`、`lib/cocreate-tools.ts`、`lib/cocreate-memory.ts`、`lib/map-types.ts`、`lib/map-storage.ts`、`lib/map-rpg-engine.ts`、`lib/memory-summarizer.ts`。

## 当前剧情提示词检查结论

以下是对当前分支的初步静态检查，不代表已经穷尽所有插件、接口和用户配置下的最终请求。

1. `lib/builtin-preset.ts` 的 `story_output_format` 是默认预设中的普通条目，包含剧情正文、摘要与写作要求，并带 `story` 标签。它不是单独藏在剧情引擎里的不可编辑指令。
2. `components/settings/preset-manager.tsx` 为非 marker 条目提供正文编辑；不会因为预设有 `builtIn` 标记就把普通正文设为只读。marker 是动态内容入口，不能与普通提示词编辑混为一谈。
3. `lib/settings-storage.ts` 的 `loadPresets` 在内置版本升级时会重新生成内置预设，保留原 ID 并通过专门函数保留自定义应用条目，并非全面保留所有用户编辑。直接修改内置普通条目存在被后续升级覆盖的风险。
4. `lib/story-engine.ts` 通过 `resolveBinding(..., "story")` 选择配置；未找到绑定预设时回退内置预设。它还读取角色记忆、近期事件、日程与世界书，交给通用组装器。
5. `lib/llm-prompt-assembler.ts` 按开关与标签处理普通条目，展开动态内容并包装历史。因此预设编辑框中的文字并不等于整个最终请求。
6. `lib/chat-engine.ts` 的 `sendLLMRequest` 还会经过插件请求处理和 provider 请求构造。`previewStoryPromptPayload` 与最终发送链路的完整一致性仍需审计，不应仅凭预览断言没有额外注入。
7. 当前检查没有发现 `story-engine.ts` 另行硬编码用户示例中的字数或叙事视角；这不是对整个软件所有请求路径的无隐藏规则保证。

实现原则：默认内置提示词可以结合新定位优化，但创作偏好必须可见、可编辑。必要的格式协议、标签与数据包装应单独说明，并检查它们是否限制创作或让用户修改后悄悄失效。输出 token 上限与正文目标字数也应分开解释。

## 第一阶段审查结果

结论：没有发现必须先做功能重构才能使用小说式主线剧情的阻碍，暂不修改运行时代码或默认预设。以下发现有明确边界，不要求用户逐项作技术选择。

- 正常剧情请求以 `story` 为活动标签。默认微信体沉浸条目带 `chat,text` 标签，不会进入该链路；关闭普通预设条目后，组装器没有专门补回该条目文本的逻辑。
- 默认 `story_output_format` 是可编辑条目，要求连续叙事、正文和摘要，但未规定具体篇幅、人称或必须禁止代写 user。文字中以 char 为中心的表述可以在将来修改默认叙事定位时一并调整，当前无需急着升级内置预设。
- 确认存在固定文字：`lib/llm-prompt-assembler.ts` 的 `getMarkerContent` 在 `charDescription` 开启时将 `You are ${character.name}.` 放在角色资料前。它不在普通预设正文编辑框里，随角色资料 marker 整体控制，不能等同于全无隐藏指令。尚未实测其对全知叙述的影响；未来若要消除身份绑定，应仅针对剧情提供可配置处理，不能直接改坏聊天与线下共用逻辑。
- 正文显示与摘要提取是不同环节。`story-parser.ts` 从原始输出提取配置的摘要标签，并兼容 `summary`；正文正则不能代替缺失的事件摘要。自定义预设可改文风，但在未另做摘要机制前应保留可识别的摘要输出。摘要缺失、编辑后旧摘要残留等进入第二阶段检查。
- 供应商适配代码主要处理角色格式、参数、工具和多模态内容；本次未发现它额外加入上述剧情文风限制。发送前插件可以改消息和部分生成参数；此审查没有检查用户设备已安装插件的行为。
- 现有调试面板已有剧情预览入口。`previewStoryPromptPayload` 经 provider 预览转换，但不执行 `llm.request` 插件变换；`sendLLMRequest` 在插件与请求构造后发布调试快照。出现差异时检查实际请求，不把生成前预览误认为最终请求。
- 内置预设版本升级重建的风险已证实。当前不升版本、不改默认条目；以后更新默认文本时优先保留用户定制，不能直接重置整套内置预设。

审查涉及：`lib/story-engine.ts`、`lib/story-parser.ts`、`lib/llm-prompt-assembler.ts`、`lib/llm-provider-adapter.ts`、`lib/chat-engine.ts`、`lib/settings-storage.ts`、`lib/builtin-preset.ts`、`components/settings/preset-manager.tsx`、`components/debug-prompt-panel.tsx` 与 `components/story/story-app-base.tsx`。
